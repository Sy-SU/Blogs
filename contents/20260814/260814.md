### Paper 2: [OpenFunGraph](https://arxiv.org/abs/2503.19199v1)

讲怎么生成 scene graph

OpenFunGraph 提出来主要是为了解决缺乏训练数据的问题。作者利用基础模型的知识来检测、描述场景中的物体与可交互元素，并推理它们的功能关系。

- 阶段 1：候选节点 detection
- 阶段 2：候选节点 description
- 阶段 3：功能关系
- 阶段 4：最终图形成

Scene Graph 的生成需要节点。OpenFunGraph 在识别这一步采取先识别物体，再识别部件的策略。

对于每张 RGB 图像，首先使用 RAM++ 进行开放图像识别。这一步不输出位置，只输出一组类别标签，然后将这些类别标签作为提示词输入 GroundingDINO，GroundingDINO 再进行定位。此时得到了每一帧里面的二维物体候选。

交互元素通常比物体小得多（例如门把手、开关等等）。直接使用 RAM++ 或者 GroundingDINO 对小部件进行检测的效果不好，因为这些部件可能只有几个像素，同时有一些类似“handle”的词缺少上下文。OpenFunGraph 先把物体标签交给 GPT-4，让它推测这个物体可能有哪些可交互部件。

LLM 同时会过滤掉不可交互的物体，例如墙壁、床等。随后把物体标签作为辅助上下文，与部件标签进行拼接（door.handle）。再将这些提示输入 GroundingDINO。

最后得到每一帧里面的**二维交互元素候选**。

接下来考虑如何将二维交互元素变成三维交互元素。对这些二维交互元素，通过读取深度、相机内参、相机位姿，将像素反投影到坐标系中。

对于来自不同帧、但在三维空间中几何一致的候选会被合并（看一下 ConceptGraph）。

为什么不能直接使用类似 “door“”handle” 这样的标签？因为标签提供的信息太少。所以 OpenFunGraph 为每个三维节点生成更完整的自然语言描述。

首先需要选择最有信息量的视角：

一个三维节点可能在很多帧中出现，但不是所有视角都同样可靠。系统用下面的分数选择前 \(N_v\) 个视角：

\[ q_i= \mathcal S^{\mathcal I_i} \cdot \frac{n_{\mathcal P^{\mathcal I_i}}}{n_{\mathcal P}} \]

其中：\(\mathcal S^{\mathcal I_i}\)：该视角的二维检测置信度；\(n_{\mathcal P^{\mathcal I_i}}\)：该视角为融合点云贡献的点数；\(n_{\mathcal P}\)：节点完整点云的点数。

这个分数同时考虑语义上是否检测得可靠以及几何上是否看到了足够多的节点区域。

接下来考虑怎么去描述物体节点。对于普通物体：

1. 从最佳视角中裁剪物体；
2. 用 LLAVA v1.6 描述每个裁剪图；
3. 用 GPT-4 汇总多视角描述。

而交互元素节点太小，直接裁剪可能只有几个像素，作者采用了两个技巧：按多个尺度扩大边界框，引入周围物体作为上下文；用红色轮廓标出真正的交互元素，引导VLM注意目标。最后使用GPT-4汇总多尺度多视角的描述。

最后需要连场景图中的边。OpenFunGraph 选择将关系分成局部关系与远程关系。

局部关系描述的是交互部件是物体的一部分，二者通常刚性连接。例如：

```
门把手 → 门
橱柜旋钮 → 橱柜
微波炉按键 → 微波炉
冰箱把手 → 冰箱
```

先用几何关系完成过滤，对于每个物体节点，检查交互元素节点是否与其三维边界框显著重叠或紧密相邻。

然后通过LLM判断语义合理性。

> 对于通过几何过滤的候选对，系统把以下信息输入 LLM：
>
> - 物体语言描述 \(\mathcal L^j\)；
> - 交互元素语言描述 \(\mathcal L^k\)；
> - 物体三维边界框 \(\mathcal B^j\)；
> - 元素三维边界框 \(\mathcal B^k\)。
>
> LLM 判断：
>
> 1. 二者是否可能刚性连接；
> 2. 该交互元素对物体执行什么功能。

例如：

```
元素：安装在白色门上的银色水平把手
物体：一扇白色室内门
几何：两个三维边界框显著重叠
```

LLM 输出：

```
关系成立
关系描述：opens
```

于是建立有向边：

```
把手 ──opens──> 门
```

所有局部关系构成局部子图：

\[ \hat{\mathcal G}^{L} = (\mathcal O^L,\mathcal I^L,\mathcal R^L) \]

远程关系的判断更加困难。例如，一个房间可能有：

- 一个开关
- 一盏吸顶灯
- 两盏桌灯

仅仅通过几何关系，很难判断出开关控制的是哪一盏灯。

在局部推理完成后，已经被识别为门把手、橱窗旋钮的这样的已经分配过的元素不再参与进一步的推理。剩下的未分配元素，例如开关、遥控器、插座，才会进入下一步远程关系推理。

接下俩，LLM 接收所有剩余交互元素和物体的自然语言描述，为每个元素提出可能控制的目标物体。

例如：

```
元素：墙上的白色灯开关
候选目标：
1. 吸顶灯
2. 左侧桌灯
3. 右侧桌灯
```

对于每个“元素-物体”候选对，系统分别取二者排名最高的视角，让 VLM 判断功能连接是否合理。

VLM 可以利用的线索包括：

- 电器是否真的插在该插座上；
- 开关是否位于吸顶灯下方的墙面；
- 遥控器外观是否像电视遥控器；
- 控制面板是否与某类设备匹配。

所有候选对的 VLM 描述会一起交给 LLM，而不是分别独立判断。

这是因为远程关系通常需要相对比较：

```
不是问“开关能不能控制吸顶灯？”
而是问“在这三盏灯中，开关最可能控制哪一盏？”
```

LLM 最终为候选连接分配相对置信度，并生成关系描述：

```
开关 → 吸顶灯：0.8，turns on
开关 → 左侧桌灯：0.15，possibly controls
开关 → 右侧桌灯：0.05，unlikely
```

系统优先保留置信度最高、最合理的连接。

远程关系形成子图：

\[ \hat{\mathcal G}^{R} = (\mathcal O^R,\mathcal I^R,\mathcal R^R) \]

最终将局部子图和远程子图合并：

\[ \hat{\mathcal G} = ( \mathcal O^L\cup\mathcal O^R,\; \mathcal I^L\cup\mathcal I^R,\; \mathcal R^L\cup\mathcal R^R ) \]

用一个房间举例，最终可能得到：

```
物体节点 O
├── 门
├── 橱柜
├── 吸顶灯
├── 两盏桌灯
└── 风扇

交互元素节点 I
├── 门把手
├── 橱柜旋钮
├── 墙面开关
└── 电源插座

功能边 R
├── 门把手 ──打开──> 门
├── 橱柜旋钮 ──打开──> 橱柜
├── 墙面开关 ──控制，置信度 0.8──> 吸顶灯
└── 电源插座 ──为其供电──> 风扇
```
